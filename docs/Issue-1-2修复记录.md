独立审查增加的两项测试在原 PR 上均失败：其余 322 项 JVM 测试通过，但自动恢复等待确认时，应用内选择通透被旧的降噪请求拦截；同一窗口内对话感知也可能触发不应发生的降噪重试。整合时修正如下：

- 应用内选择新模式前，仅取消自动恢复拥有的待确认请求，使新选择能够发送；不清除其他用户请求。
- 独立跟踪对话活动，不依赖“对话时降低手机音量”开关。对话开始时取消恢复，已在对话中摘耳也不启动补偿；对话结束或关闭对话感知后解除抑制，重建会话时清理该状态。
- 如收到原生长按回报，取消此次自动恢复，不额外开启自定义按压拦截。不能保证所有固件都上报长按；紧邻摘耳的物理操作仍有协议层识别边界。
- 非等待确认的辅助设置不再长期显示“命令已发送”。开关与滑块仍采用成功写入后本地更新，真实写入失败仍显示错误；未回报来源信息保留在诊断页，而不是计时伪造成功。
- 诊断新增尚未读取的具体设置、已发送未回报的设置、最近真实聆听模式、单耳权限的真实回报与本地请求，以及恢复尝试次数。真实回报单独保存，不能被本地乐观更新覆盖；无效设置值不能清掉未确认标记或覆盖有效值。共享报告继续只输出固定字段及白名单设置名称，不包含设备地址、序列号或原始包。

本节的单元测试和模拟器操作验证不等同于实机声学效果验收；PR 作者的实机反馈归属及适用范围见下文。本轮不发布发行版，也不自动关闭 Issue #2。

## 构建 26：PR 原始单耳降噪方案与反馈

Issue #2 的构建 24 反馈确认滑动音量、耳机提示音实际上生效；“尚未回报”提示长期存在不代表这两项失效。剩余单耳降噪的明确复现为：双耳佩戴并开启降噪，摘下一只后另一只自动解除降噪，即使开启“单 AirPod 时降噪”仍会发生。用户提供的是硬件版本 `1.0.0`，不能据此推断固件版本。

- 已核对上游的 `ONE_BUD_ANC_MODE (0x1B)` 开/关值也是 `1/2`，不猜改协议编号、功能标志或其他配置，也不把成功入队伪装成耳机确认。
- 为受影响的 AirPods 5 无线充电盒款增加手机侧兼容。仅在单耳权限为开启、已有真实降噪模式回报且从双耳佩戴变为单耳时，重申 `0x1B = 1`，再请求 `LISTENING_MODE (0x0D) = 2`。不会从通透、自适应或关闭模式主动开启降噪，不影响其他型号。
- 耳机可以先回报自动切换后的模式，再回报摘耳；保留最多 1 秒的相邻事件关联。若模式回报晚于佩戴回报，也只在这 1 秒内最多重试一次。降噪确认后不再接管后续物理切换，不使用轮询或无限重发。紧邻摘耳的物理模式切换无法与固件自动回退完全区分，因此不持续维持目标模式。
- 应用内主动选择其他模式、关闭单耳开关、摘下全部耳机、控制通道重建或断连，都会取消这次恢复。单耳权限写失败不发送后续模式命令；模式写失败和确认超时沿用现有错误反馈。
- 辅助设置的“已发送”文案说明部分固件可能不回报、应以实际效果为准；它是状态来源说明，不是等待中的请求，也不是已确认。真正等待模式确认的操作仍显示等待和超时错误。

以上属于有界的主机兼容措施，并不能证明固件忽略单耳权限的内部根因。以下为小米 17 Pro、`4.0.4.0.XBLCNXM.D01` 与原 AirPods 5 无线充电盒款的验收清单：

1. 开关关闭时，双耳降噪后摘下一只，不应新增恢复写入。
2. 开关开启时，分别摘左耳和右耳，确认剩余耳机的实际降噪持续有效，而不只检查界面。
3. 单耳使用时主动改通透、自适应或关闭，确认不会持续被拉回降噪；回到双耳后重复测试。
4. 在恢复期间关闭开关、摘下全部耳机或断连，确认不重发；控制失败时应显示真实错误。
5. 复测已修复的麦克风、长按循环、提示音和滑动音量；首次未连过 iPhone 的耳机初始化仍需独立验收。

本地自动化验证（2026-10-21）：322 项 JVM 测试全部通过，无失败或错误，其中新增 5 项纯状态机测试和 7 项实际控制器/协议链路回归，覆盖左右耳摘下、模式回报乱序、1 秒关联边界、重复回报、主动选择其他模式、关闭开关、全部摘下、会话重置及写入失败。初轮测试发现合成会话夹具未重置新增状态，补齐会话隔离后完整 JVM 回归通过。`lintDebug` 为 0 错误、120 条警告；Debug/Release 构建均通过，两个 APK 的 `versionCode` 均为 26，Release APK 签名校验通过。首次本地构建使用插件回退的 Android Debug 签名，随后测试包使用用户本地密钥重新签名并安装；密钥及密码不纳入仓库。未执行 Android 仪器测试，不以这些自动化结果代替实际降噪验收。

## 构建 25：展开卡片继续裁字的后续调整

用户在构建 24 后仍观察到断开按钮文字被裁切。本轮按反馈移除卡片中间分隔线，收紧下方名称与按钮区域，并补充文字测量修正：

- 仅处理带 HyperPods 归属标记的卡片。将 `ModuleTextButtonViewHolder` 的 `line` 设为 `GONE`，而不是只改透明度；系统底部手势短条不修改。
- 这条线和下方内容的间距互不依赖，因此还需分别缩减 `layout_hint` 与 `focus_button_container` 的顶部间距，最多 8dp，保留非负余量，不修改底部留白。不使用 `translationY` 偏移，排版和点击区域保持一致。
- 已提供插件的 `focus_notification_module_mark_4` 中，按钮外层高度为 `WRAP_CONTENT`，内部行却为 `MATCH_PARENT`。对 HyperPods 将内部行改为 `WRAP_CONTENT`，保留上一版的完整字体行框，让测量使用实际文字高度，而不是只增加字体留白。
- 保存上述改动前的值，下一次绑定前还原；重复刷新不累加上移距离，不把样式带到其他通知。内部行用弱引用保存，避免复用缓存间接保留整棵视图树。

静态依据：同一插件 APK（SHA-256 `7a0dfbe892f558393ad28ae8aea2a12fe152de972354b067500ed16ca9e17f3e`），REA 方法证据 `ev_eb0432461f3f70bb768e578484d7a362d4bbfe40bf4c6af761f4f26eae6e68fd` 确认 `ModuleTextButtonViewHolder.initView` 的资源及视图入口。AAPT2 资源映射和 XML 解码确认 `focus_notification_module_button_2` 对应 `res/fPL.xml`、`focus_notification_module_mark_4` 对应 `res/q5k.xml`，前者按钮顶部间距 19dp、名称外层顶部间距 4dp，后者含上述高度嵌套。静态结构并不能证明目标手机运行时裁切的唯一原因。

验证：310 项 JVM 测试通过；仿照该插件层级构造原生 Android 布局，在 1.0/1.3/1.6 倍字体下验证分隔线不占位、按钮上移、完整字体高度与上下边距可容纳、回收还原，共 9 项通过。Debug/Release 编译通过，Lint 0 错误、121 条警告。这些是原生测量和结构验证，不等同于小米 SystemUI 真机验收；安装构建 25 后应重启相关系统进程或手机，再确认通知和展开卡片实际效果。

## 初始化与恢复的边界

电量、佩戴、型号以及支持型号的当前听音模式，是可用状态的基础。辅助设置暂未返回，不应让已正常工作的电量/降噪页面一直显示初始化中。

后台仍按原来的有限次数请求缺少的设置；不会因为缺少辅助设置而关闭有效控制通道。诊断页继续保留缺少设置数量。仓外耳机缺少有效电量、型号或佩戴状态时，仍走原有恢复流程，不使用旧缓存冒充新回报。

以下行为保持不变：

- 听音模式与 Pro 型号的“允许关闭模式”前置条件仍等待耳机确认。
- 按压速度、长按时长、滑动速度和自适应强度不在本轮扩大即时更新范围。
- 不实现 ATT、双设备接管或新的按压自定义功能。
- 不新增通知权限、敏感日志、账号配置或凭据。
